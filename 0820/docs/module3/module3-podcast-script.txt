大家好，歡迎回到深度解析節目，這是系列的第三集。前兩集我們把環境搭好了，也把考古題 PDF 變成了一題一張乾淨圖片、加上一份標準答案的問題集資料夾。這一集要處理的問題是：拿到這個問題集資料夾之後，要怎麼把它變成一個學生可以自己打開作答、老師事後可以收成績的測驗網頁？

這裡要先說明一個很重要的設計。其實工作坊講師早就已經寫好一個叫 build-quiz-app 的現成工具，一句話就能請 Codex 用它，把整件事情做完，那是第四個模組要教的捷徑。但這一集，也就是第三個模組，刻意不直接套用那個現成工具，而是從只有一個問題集資料夾這個起點出發，一步一步請 Codex 幫你分析需求、設計資料結構、寫出網頁樣板跟打包程式。目的是讓你搞懂這整套工具背後到底在做什麼，而不是只學會下一句咒語。等你做完這一集的流程，你會發現自己造出來的東西，其實就是在重新發明那個現成工具已經做好的輪子；那時候再回頭用第四模組的捷徑，你會很清楚每一步在幫你省掉什麼。

整個設計，如果濃縮成一句話，其實就是你會對 Codex 說的一句話：我手上有一份題目跟正確答案，麻煩幫我做成一個學生可以自己打開作答、我事後可以收學生成績的網頁。不用先弄懂任何技術名詞，就跟你平常請人幫忙做事一樣，把你想要什麼講清楚，剩下技術上怎麼做，交給 Codex。接下來，會照七個步驟，一步一步跟 Codex 討論、確認。

第一步，是先決定產出的東西要放在哪裡。工具產生出來的設定檔、樣板、打包程式、最終成品，該放在哪，才不會跟問題集資料夾攪在一起，之後也方便換資料？合理的做法，是固定放在問題集資料夾的同層，不是塞進問題集資料夾裡面。如果問題集資料夾是 repo 底下的某個資料夾，工具的輸出，就放在跟 repo 平級的 app 資料夾。這樣以後問題集資料夾即使被整理、封存或換掉，這個當作引擎的 app 資料夾，也不會受影響。這一步的重點，是先跟 Codex 討論架構，而不是丟一句指令就期待它自動生出整套東西。

第二步，是分析問題集資料夾的形狀。在動手設計設定檔、寫網頁樣板之前，得先知道這個問題集資料夾實際長什麼樣子：答案 JSON 在哪、有幾題、圖片放在哪個子資料夾、檔名有沒有規律。這一步的交付物，是一支只讀取、不寫入任何檔案的分析腳本，請 Codex 用 Python 標準函式庫寫，掃描資料夾之後印出一份 JSON 報告。報告裡至少要有幾個欄位：找到的答案檔名跟題數、圖片放在哪個子資料夾——如果圖片跟答案檔案放在同一層，這裡會寫一個點，代表當層目錄；keys 檔裡有寫但找不到對應圖片的題目清單；還有從圖片檔名試著推論出來的規律，像是題號、科目代號，抓不出規律就不硬湊。這幾個欄位每一個都有它的用意：題數要跟你預期的對得起來，缺圖清單如果不是零，代表打包時要先決定怎麼處理這些題目；檔名規律如果分析不出來，代表這組檔名沒有清楚規律，網頁樣板就要準備一個備案，退回逐題顯示原始檔名。

第三步，是設計設定檔的資料結構，也就是 config.json。這裡要解決的問題是：怎麼用一份設定檔描述「一份測驗」，還要讓同一套工具之後能疊加好幾份測驗，不用每加一份就重新設計格式。合理的做法，是設計一個叫 assessments 的陣列，每一筆對應一份測驗。每一筆至少要能描述：測驗名稱，這會變成輸出檔名的一部分，所以陣列裡每一筆的名稱一定要不一樣，撞名會互相覆蓋；問題集資料夾的相對路徑；答案檔名；圖片子資料夾；這份測驗預設要抽幾題，這裡的巧思是，這個數字不是原始題數，而是每次作答預設抽幾題，可以設計成用一個上限公式，比如二十題跟原始題數兩者取比較小的那個，避免一次抽太多題拖慢作答，但學生開始作答時，仍然可以自己把題數改成一到全部題數之間的任何數字；還有可選的答案字母，以及檔名規律，這個欄位可以省略。如果是對已經有內容的設定檔疊加新測驗，切記要先讀出既有內容，用陣列新增一筆的方式加進去，不要把整個檔案覆蓋掉，不然會把之前疊上去的測驗設定弄丟，這也正是為什麼要設計成陣列，而不是單一物件的原因。

第四步，是打造學生實際會打開的那個測驗網頁樣板。這裡有一個核心設計限制，我覺得是整個模組裡最重要的技術知識點：最終交付的檔案，必須能直接雙擊開啟，不能依賴任何伺服器。瀏覽器基於安全性的考量，會擋掉 file 開頭路徑底下、用 fetch 函式讀取外部檔案的行為，所以最終版本，絕對不能用 fetch 去讀取設定檔或圖片，所有資料都必須直接內嵌在 HTML 檔案裡面。這一步的產物，其實是兩種版本並存的設計：一份是可以編輯的原始碼版本，開發階段可能還是用 fetch 讀一份假資料方便邊改邊測，本機測試的時候需要另外開一個伺服器；另一份，是下一步打包出來的、雙擊即用的成品，資料已經內嵌，不需要伺服器。分清楚這兩種版本的差別，是這一步最重要的設計決定。網頁本身要做到的功能，包括讓學生輸入姓名、選擇這次要抽幾題、隨機抽題並依序顯示每題的圖片跟選項、全部作答完送出後顯示總分跟每一題的對錯，還有一顆按鈕，把這次作答的逐題結果下載成 CSV 檔，檔名要帶學生姓名跟時間戳記，方便老師之後合併多份成績單。

第五步，是寫打包程式，把設定檔裡每一筆測驗指到的圖片，逐一轉成 base64 字串，塞進第四步的樣板裡，輸出成一個完全自包含、不需要伺服器、不需要網路的 HTML 檔案。這支打包程式，不加參數的時候，預設重建全部測驗；加上指定測驗名稱的參數，就只重建那一筆，其他已經是最新的檔案不會動，這一點很實用，因為每份測驗打包出來，檔案都可能好幾十 MB，重新打包全部只是浪費時間。每一筆處理完，應該印出檔名、題數、檔案大小；如果有圖片缺檔，印出警告，但不要讓整個打包程序中斷；最後印出一行「Built 幾之幾份測驗」的總結，這一行的兩個數字如果不相等，代表某一筆被跳過了，要往上找對應的警告訊息，通常是路徑設定寫錯。輸出檔案的大小，大約會是來源圖片總大小的一點三七倍，因為 base64 編碼會讓檔案膨脹大概百分之三十七，如果輸出檔案明顯小很多，通常代表大部分圖片沒被塞進去。

第六步，是驗收成果，這裡有一句話我覺得很值得記住：不要只信任腳本沒有報錯。要確認 dist 資料夾底下每份預期的檔案都存在，檔案大小落在合理範圍；然後真的直接雙擊，或者用瀏覽器開啟本機檔案路徑，打開那個檔案，不要另外開伺服器——整個重點，就是要驗證「不架站也能用」；輸入姓名、選一個較小的題數、作答幾題、按送出，確認會出現分數跟逐題對錯畫面。

第七步，是打造教師端的成績彙整頁。學生在測驗頁面送出作答後，會下載一份 CSV，這一步要設計一個給老師用的頁面，把全班這些 CSV 檔合併起來看，一樣要能雙擊開啟、不需要架站，也不能把任何資料上傳到網路上。這個頁面要做到：可以把多個 CSV 檔拖曳到頁面上；依考試名稱自動分組，列出每位學生答對題數跟總題數跟正確率，還有每一題的出現次數跟答對次數跟答對率兩張表；並且提供匯出合併 CSV，跟列印或存成 PDF 這兩個功能。這裡特別值得一提的是「每一題的答對率」這張表，特別適合用來看哪幾題全班普遍答錯，回頭檢討教學重點。

七個步驟做完之後，模組安排了一個動手做的練習：拿一組全新的問題集資料，看看第二步到第五步做出來的分析腳本、設定檔設計、打包程式，能不能不修改、原封不動地套用上去。如果可以，代表這套工具的設計是對的；如果每換一組資料就要改工具本身的程式碼，代表某個環節設計得不夠通用，值得回頭檢討。這其實是驗證「自己造的工具是否真的可以重複使用」最直接的方式。

聽到這裡，你可能會覺得，這一集內容也太細了吧，直接用現成的捷徑不就好了？我想模組的用意，其實就在標題那句話：先自己設計一次，才會真正懂這套工具在做什麼；等你之後遇到報錯、需要手動調整設定、或者檔名沒有清楚規律的情況，你才有能力回頭排查問題，而不是只能重新呼叫一次現成的工具、然後不知道哪裡出了狀況。好，那第三集就先到這裡。下一集，我們會看看第四個模組怎麼用一句話，直接呼叫現成的工具，把這整套流程濃縮成最短路徑。謝謝收聽，我們下一集見。
